# Agent Application Development 分析计划

## 1. 研究目标

这组笔记用于从真实项目出发，建立一套可复用的 Agent 应用开发知识框架。研究包含两条目的不同、但可以互相参照的主线：

- 对 QM、Omnigent、DeepSeek Harness 三个较成熟的开源项目进行学习、分析和比较。
- 对当前自有项目 AI Manus 进行现状分析，说明已有架构、模块、技术和不足；具体优化与改造方案留到后续单独讨论。

研究对象包括：

- **QM**：重点参考其应用核心、Session/Turn、Harness、工具、审批、Sandbox 与持久化设计。
- **Omnigent**：重点参考其 Server、Host、Runner、Harness、Agent Runtime 分层，以及控制面与执行面的关系。
- **DeepSeek Harness（DSH）**：不把它视为与 QM、Omnigent 完全同类的平台，重点研究 Cordis、插件组合、服务注入、生命周期、事件和能力 seam 等解耦方法。
- **AI Manus**：当前自有 Agent 应用项目。重点说明现有架构、主链路、模块职责、技术实现和可观察到的不足，不在总览阶段展开具体改造设计。

## 2. 总体分析原则

### 2.1 先逐项目讲清，再进行横向比较

总览中的架构分析先分别还原 QM、Omnigent、DSH 和 AI Manus 的系统边界、整体架构、主要组件、运行流程与技术选择，使每个项目本身形成完整认知；随后再按统一维度进行横向比较。

逐项目分析采用统一结构：

1. 项目解决什么问题，系统边界在哪里。
2. 总体架构、关键组件和目录或进程边界。
3. 一次 Turn、工具调用等关键流程如何运行。
4. 各组件使用什么技术，以及技术选择带来的收益和代价。
5. 项目最有代表性的架构特点。

横向比较再回答同一职责在四个项目中由谁拥有、如何实现、为什么不同。这样既避免只看对比表导致整体认识碎片化，也避免四份独立源码导读缺少共同参照。

### 2.2 不强求四个项目机械对齐

四个项目的产品边界不同，某个能力不存在或由外部系统负责，不等于设计缺陷。比较时应回答“这项职责由谁拥有”，而不是只查找同名目录或类。

尤其需要保持以下区别：

- QM 与 Omnigent 更接近应用核心或平台控制面，可以直接比较 Session/Turn、Harness、工具、审批和 Sandbox 等职责。
- DSH 更接近可组合 Harness 与插件运行时，应重点研究模块解耦和能力组合，不强行要求它拥有完整产品控制面。
- AI Manus 是当前产品与运行时的结合体，先如实分析当前实现；候选目标边界不在总览阶段预设。

### 2.3 事实、解释和建议分开

- **代码事实**：能够从当前源码、配置、测试或项目文档中直接确认。
- **架构解释**：基于多个代码事实归纳出的职责、边界和设计取舍。
- **后续问题**：分析中发现但尚未展开的优化或改造问题，只记录为待研究问题，不在总览中直接给出方案。

### 2.4 固定源码版本和真实调用链

每轮正式分析都要记录仓库、分支、Commit 和分析日期。结论必须尽量追踪到生产入口、核心对象、状态变化、通信协议、持久化位置和失败行为，避免只根据 README 或目录名称判断。

## 3. 总览阶段规划

总览阶段计划形成 **2 个正式文件**。数量保持较少，每个文件职责明确。

### 3.1 `overview.md`：研究入口与内容导航

这是整个专题的入口页，主要回答“这四个项目分别在解决什么问题，以及它们之间是什么关系”。

计划包含：

- 研究目的与两条研究主线。
- 四个项目在本专题中的角色。
- 基于源码、固定版本、区分事实与解释的研究方式。
- 四个项目的一句话定位和内容地图。
- 已有基线材料。
- `architecture.md` 和后续模块分析的导航。

该文件只承担入口和导航职责，不提前给出 AI Manus 改造结论，也不把某些项目能力预先排除在分析之外。

### 3.2 `architecture.md`：技术栈、逐项目架构与横向比较

该文件是总览阶段的主体。技术栈与组件职责放在一起解释，不再单独创建 `technology-stack.md`。

计划包含：

- 文件前部提供一张四项目技术栈全景表，先回答各组件使用了什么。
- 依次讲解 QM、Omnigent、DSH 和 AI Manus 的定位、总体架构、主要组件、主流程、状态与执行边界。
- 在每个组件内部说明实际技术栈，并分析不同选择对应的约束、收益和代价。
- 逐项目分析完成后，再按控制面、Harness/Runtime、进程通信、状态持久化、工具审批、Sandbox、模块解耦等维度横向比较。
- 使用架构图、部署拓扑图、Turn 流程图和工具审批流程图解释静态关系与动态行为。
- 末尾归纳成熟 Agent 应用的共同模块、主要差异和后续模块分析入口。
- 增加技术概念附录；正文首次出现陌生概念时先用一句话解释，附录再解释 JSON-RPC、SSE、WebSocket、Unix Domain Socket、Harness、Runtime Adapter、依赖注入、事件总线等概念。

图的目标是解释职责和数据流，不追求把所有目录和类都画进去。AI Manus 章节以当前架构与不足分析为主，不在本文展开完整改造方案。

## 4. 总览内容的呈现方式

总览采用“逐项目完整讲解 + 统一维度横向比较”的混合形式。

每个项目先使用以下结构：

```text
项目定位与系统边界
  ↓
技术栈与总体架构图
  ↓
主要组件、进程与目录边界
  ↓
关键运行流程
  ↓
架构特点、技术选择及代价
  ↓
源码证据索引
```

逐项目讲清后，再按同一职责进行横向比较：

```text
共同问题与比较口径
  ↓
四项目横向对比表
  ↓
必要的实现差异说明
  ↓
技术选择、收益、代价与适用条件
  ↓
源码证据索引
```

不采用以下两种极端写法：

- 只做一张大表：信息过于压缩，无法解释单个项目的真实调用链和设计原因。
- 只逐项目从头讲到尾：相同主题缺少共同参照，不容易看出架构差异。

四个项目的篇幅不要求完全相等。DSH 不拥有的产品层职责应明确标为“不在其系统边界内”，而不是为了表格完整强行寻找对应物。

## 5. 架构图与流程图规划

总览阶段优先规划以下图：

1. **项目架构图**：分别解释 QM、Omnigent、DSH 和 AI Manus 的主要组件与责任边界。
2. **四项目架构映射图**：把同一职责在四个项目中的组件对应起来。
3. **部署与进程拓扑图**：展示 Server、Host、Runner、Harness、Runtime、Sandbox、数据库和对象存储的真实边界。
4. **Turn 端到端时序图**：从用户输入到模型输出、事件持久化和前端更新。
5. **工具与审批时序图**：展示工具定义、模型发起调用、策略判断、人工审批、实际执行和结果回传的控制权。
如果一张图已经能表达清楚关系，不为每个项目机械复制一张同类图。

图使用 Archify 生成和校验。Markdown 是主要阅读载体；专题目录内同时保存图的 JSON 规格、可交互 HTML 和用于正文预览的 SVG。正文通过标准 Markdown 语法内嵌 SVG，使 VS Code 等 Markdown 编辑器无需跳转即可阅读，再在图下保留一个相对路径的交互版 HTML 链接；同一路径同时适用于本地阅读和 Quartz 站点。SVG 使用矢量格式，不额外导出 PNG、JPEG 或 WebP。

- 权限、跨域 iframe、动态页面、标签页绑定、隐私和审批等真实边界。
- 浏览器内读取与后端 `web_search` / `web_fetch` 的职责分工。

### 6.12 每篇模块都要回答的固定问题

为了避免模块页变成“概念词典”，后续每篇都使用同一组问题检查四个项目：

1. **谁拥有这项能力**：控制面、Session、Turn、Harness、Runtime、Host、Sandbox 或前端，哪个对象是事实来源。
2. **一次请求怎样走完**：从入口、状态变化、事件、外部调用到终态，画出一条能追到源码的调用链。
3. **前端看见什么**：初始快照、增量事件、断线重连、重复事件、等待审批和后台运行分别怎样表示。
4. **数据存在哪里**：业务事实、短暂队列、游标、二进制文件、运行时句柄和缓存分别由谁保存。
5. **失败后怎么办**：进程重启、网络断开、消费者太慢、工具重复执行、审批超时、Sandbox 消失时，系统如何恢复或明确报错。
6. **边界怎样保护**：身份、Workspace/路径、工具权限、网络、凭据、成本和资源上限在哪里检查。
7. **生命周期怎样结束**：Turn、Task、Session、Sandbox、后台进程、附件和订阅何时关闭、保留或删除。
8. **实现为何不同**：把技术选择与产品边界、部署形态、可靠性要求联系起来，不只罗列框架名称。

贯穿各篇的重点观察项包括：Turn 生命周期与前端会话状态联动、Skill 是目录索引还是要复制进 Sandbox、定时任务如何创建一次新的执行、附件与 Artifact 的跨进程边界、事件游标与幂等、子 Agent 的所有权、成本/配额、权限/审批、保留与删除、协议版本和测试证据。它们是检查清单，不代表每个项目都必须拥有同样的实现。

## 7. AI Manus 的分析口径

AI Manus 作为自有项目单独分析，并在横向比较中正常出现。重点回答：

1. 当前是否已经有对应能力。
2. 对应入口、核心类、状态和基础设施在哪里。
3. 当前实际使用了哪些技术。
4. 当前实现的责任边界是否清楚。
5. 与 QM、Omnigent、DSH 相比，差异来自产品目标还是实现不足。

总览只记录能够由源码支持的现状、特点和不足，不要求每一处分析都给出改造建议，也不以“像不像某个开源项目”作为评价标准。具体优化方案留到后续独立研究。

## 9. 建议执行顺序

1. 固定四个仓库的版本，建立术语和证据清单。
2. 逐项目完成架构、技术栈和真实调用链分析，形成 `architecture.md`。
3. 在同一文件中完成横向比较、共同模式归纳和技术概念附录。
4. 使用 Archify 生成和校验必要的架构图与流程图，并在 Markdown 中链接交互式 HTML。
5. 最后形成 `overview.md`，作为研究入口和内容导航。
6. 根据总览中暴露出的真实边界，确认模块拆分。
7. 逐个完成 models/ 下的十篇通用模块分析和浏览器插件横切专题，并回填导航。

当前已完成总览与第一版模块分析；本轮会把上述固定问题和配套图补入模块页。后续更新应继续记录源码版本，并在具体模块页中增量深化；若某个项目没有某项能力，要明确写成“当前源码未发现”，而不是用推测填空。
